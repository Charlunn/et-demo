# ADR 0003 · 前端用 Streamlit 做产品工作台, 而非 API 调试器

## 状态
Accepted

## 背景
demo 的核心判准 (PRD §2.1 / SPEC §3.7) 是: 把前端交给一个不懂 API 的人, 他能走完
"看行情 → 做报价 → 看出清 → 对账 → 复盘"整条真实业务路径, 而不是点"发送请求 / 看 JSON 响应".
前端是产品的脸, 不是 Postman 的脸.

## 决策
用 **Streamlit** 单入口多页 (pages/ 自动生成侧边导航) 做 5 个**业务 tab** (非技术 tab):
1 行情看板 / 2 报价工作台 / 3 出清与计划 / 4 结算对账 / 5 回测复盘.
- 每页是一个**业务动作的闭环**: 选业务对象 → 看业务含义可视化 → 改业务参数 → 看业务结果.
- `api_client.py` 是后端唯一通道 (httpx), 页面禁止裸 URL / `requests.post` / 手填 JSON 传入体.
- 前端**不内置领域公式计算**: 一切数值来自后端 API (单源真理), 前端只呈现与收集参数.
- 主题: 单一品牌主色 (电力青绿) + 2 中性辅色, 浅背景深字; 禁花哨发光/玻璃拟态/渐变彩虹.

不用 React/Next SPA (1h 内做不出稳定企业感, 且与"产品工作台搬进对方系统"语义不符).

## 理由
- Streamlit 自带企业感卡片/表格/表格/图表, 快速且克制; 单布局 + 侧边导航即覆盖五业务页.
- "前端不内置公式"使工作台作为"可搬进对方系统"的交付物成立 — 它依赖后端 API 契约而非内置计算.
- Postman 式调试器是失分判准; 业务闭环是加分判准; Streamlit 多页正落于此.

## 后果
- 正面: 1h 内可交付五业务闭环产品工作台; 烟测用 AppTest 验证可渲染且包含五页导航.
- 负面/边界: 复杂交互不如 SPA 灵活; 但 demo 的克制定位恰好需要它, 而非它的缺点.

## 相关
